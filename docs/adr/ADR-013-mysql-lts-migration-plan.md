# ADR-013 — План перехода с MySQL 8.1.0 на LTS

Статус: **Предложение; версия и дата перехода владельцем не утверждены**  
Дата: 2026-09-28

## Контекст

ADR-008 и текущая поставка требуют MySQL ровно 8.1.0. Это выпуск Innovation:
согласно [модели Oracle](https://dev.mysql.com/doc/refman/8.4/en/mysql-releases.html),
поддержка таких выпусков заканчивается при выходе следующего Innovation. Для
долгой эксплуатации предпочтителен поддерживаемый LTS. В
[матрице переходов Oracle](https://dev.mysql.com/doc/refman/8.4/en/upgrade-paths.html)
описан путь из Innovation к следующему LTS; кандидатом для этой линии является
MySQL 8.4 LTS. Наличие именно 8.4 в Amvera и порядок миграции их управляемого
сервиса пока не подтверждены. [Инструкция Amvera по MySQL](https://docs.amvera.ru/databases/mysql.html)
не обещает конкретную версию; для бэкапов указывает тариф «Начальный Плюс».

## Предлагаемое решение

Подготовить **новый изолированный сервер 8.4 LTS**, перенести на него копию
данных логическим dump/load, проверить приложение, а переключение выполнить
отдельным окном обслуживания. Это предпочтительнее изменения бинарника
действующей БД на месте в условиях управляемого сервиса. Выбор целевой patch
версии, тарифа, площадки и даты требует подтверждения владельца и поставщика.
До этого ADR-008 действует без изменений: production, CI, тестовые стенды и
`EXPECTED_VERSION` по-прежнему требуют 8.1.0. Этот документ не разрешает
автоматическое изменение версии или платного тарифа.

## Порядок подготовки и приёмки

1. Получить от Amvera или системного администратора список доступных 8.4.x,
   способ создания отдельного сервиса, его стоимость и ограничения по dump/load.
   Определить ответственного, окно обслуживания, RPO/RTO, срок хранения и
   доступность off-host копии. Для текущей Amvera-беты без проверенного
   восстановления реальных данных переход блокирован.
2. Снять зашифрованную копию 8.1.0 и восстановить **в отдельную пустую БД** по
   `docs/runbooks/backup-restore.md`; записать checksum, дату, версии и
   фактическое время восстановления без персональных данных в отчёте.
3. Запустить [MySQL Shell Upgrade Checker](https://dev.mysql.com/doc/refman/8.4/en/upgrade-before-you-begin.html)
   на копии, исправить все несовместимости. Сравнить schema/migration state,
   charset/collation, generated columns, FK, индексы, JSON и планы критических
   запросов до и после загрузки.
4. На 8.4 выполнить все SQL-миграции с чистого состояния и восстановление
   исторической копии. Прогнать unit/API/E2E, Scanner offline sync, импорт
   5000 вымышленных студентов, конкурентные регистрации/capacity, объединение
   профилей, утверждение ведомости и идемпотентное начисление. Сравнить
   агрегаты регистраций, посещений и баллов без выгрузки персональных данных.
5. Только после зелёной приёмки обновить проверку точной версии, CI, release
   scripts, deploy/runbooks и ADR-008 единым изменением. Проверить staging
   развертывание на новой БД и резервный способ возврата.
6. Перед переключением остановить запись, сделать последнюю согласованную
   копию, загрузить её в 8.4, повторить проверки и переключить секрет подключения.
   Возврат возможен к сохранённой 8.1.0 БД **только до возобновления записи**;
   после новой записи требуется отдельная сверка и восстановление из копии,
   а не попытка in-place downgrade.

## Обслуживание зависимостей

Проверять уязвимости в CI и обновлять Python/TypeScript зависимости небольшими
группами с lockfile, тестами и просмотром changelog. Отдельно разобрать
предупреждения Starlette TestClient/httpx и Pydantic alias; не менять их вместе
с версией MySQL, чтобы причины возможных регрессий оставались различимыми.

## Необходимое решение владельца

Подтвердить целевую LTS patch-версию и инфраструктуру после проверки
доступности Amvera, стоимость нового сервиса и хранения резервных копий,
ответственного за восстановление, RPO/RTO и окно переключения. До этого R25
остаётся открытым.
