# 05. Domain Model

Статус: **Release 1.0 domain model**

## 1. Базовые сущности

### Person
Реальный человек в общей базе. Один Person может участвовать в нескольких мероприятиях.

### Event
Отдельное мероприятие/день мероприятия.

### EventFormField
Дополнительный вопрос конкретного Event.

### EventStream (локальное обновление после r2)
Один временной поток внутри Event: название, интервал, лимит мест, порядок и
признак доступности записи. Registration.stream_id связывает запись с потоком
того же Event. У одного Person по-прежнему одна ACTIVE Registration на Event,
а не по одной регистрации в каждом потоке. История не удаляется при отключении потока.

### Registration
Связь Person с конкретным Event. Хранит snapshot базовых персональных данных на момент регистрации и отдельный QR.

### RegistrationAnswer
Ответ Registration на конкретный EventFormField. Ответы вынесены из Registration, чтобы изменение формы не превращало исторические данные в бесструктурный JSON.

### AttendanceEvent
Факт/попытка отметки посещения. Модель событийная, а не boolean-only.

### StaffUser
Служебный аккаунт сотрудника.

### EventAccess
Права сотрудника на конкретное мероприятие.

## 2. Person ≠ Registration ≠ StaffUser

Сотрудник может быть Person/Participant одного события и StaffUser/Scanner другого.

## 3. Registration snapshot

Registration повторяет ключевые поля Person на момент участия:

- ФИО;
- дата рождения;
- email;
- телефон;
- группа;
- тип участника;
- организация.

Это сохраняет исторически корректный отчёт, даже если Person позже поменял группу или контактные данные.

Тип участника принимает значения `KAIT_STUDENT`, `KAIT_TEACHER`, `EXTERNAL_STUDENT`, `EXTERNAL_TEACHER`, `PARENT`, `OTHER`. Учебная группа относится только к `KAIT_STUDENT`; организация запрашивается только у внешнего студента или сотрудника согласно настройкам формы, автоматически задаётся для участников КАИТ и отсутствует для `PARENT`/`OTHER`.

## 4. QR

QR принадлежит Registration, а не Person. Для каждого Event — отдельный QR. Payload состоит из случайного `public_id` Registration и серверной подписи. Персональные данные в payload не помещаются.

## 5. Дедупликация

Автоматическое объединение только по ФИО запрещено.

Для публичной/onsite регистрации сильным совпадением считается одно из условий при совпадающем нормализованном ФИО:

1. тот же `email_normalized`;
2. тот же `phone_normalized`;
3. та же дата рождения.

Если сильные идентификаторы указывают на разных Person, автоматическое объединение запрещено: создаётся отдельная запись и ситуация помечается для административной проверки, чтобы не повредить данные другого человека.

Для Excel строки с `ФИО + группа + организация` без сильного идентификатора показываются как вероятное совпадение на preview и не объединяются молча.

## 6. Повторная регистрация на тот же Event

После уверенного Person match сервер проверяет активную Registration `(event_id, person_id)`. Если она уже существует:

- новая Registration не создаётся;
- публичный запрос не изменяет Person, Registration, выбранный поток или ответы формы;
- публичный ответ не содержит `registration_id`, `ticketUrl` или другую возможность получить существующий билет;
- билет повторно ставится в email queue только на email, сохранённый в существующей Registration; новый email из повторной формы не используется;
- если сохранённого email нет, участник должен обратиться к организатору;
- авторизованная очная регистрация организатором/сканировщиком остаётся отдельным административным сценарием и может актуализировать существующую запись в пределах его полномочий.

## 7. Attendance

Основной факт посещения определяется как первое валидное событие. Повторные scans могут храниться, но не меняют `first_attended_at`.

## 8. Capacity

Capacity считают только активные Registration. `ANNULLED` не занимает место. Участник сам отменить Registration не может, но SUPER_ADMIN/ORGANIZER может аннулировать ошибочную/дублирующую запись и тем самым освободить место.

Назначенный SCANNER может явно подтвердить превышение мест при очной регистрации; сервер проверяет EventAccess и сохраняет факт в аудите.

## 9. Global Person directory

SUPER_ADMIN/ORGANIZER может искать Person глобально и видеть историю Registration. Редактирование актуального Person не переписывает snapshots прошлых Registration.

## 10. Participation и активность

Registration, AttendanceEvent и Participation — разные факты. Participation
создаётся для существующих Person + Event + Registration и хранит роль, результат,
поток и состояние подтверждения. Баллы хранятся неизменяемыми проводками, а не
редактируемым итоговым числом. Полная модель, приватность профиля и правила
пересчёта описаны в [контуре активности](./ACTIVE-INTEGRATION.md).

Для новых Events `StudentRosterMember` помечает проверенного студента в общем
контингенте, а `EventParticipationReview` хранит итоговое решение отдельно от
сырых отметок Scanner. `Event.activity_review_state` переходит
`NOT_STARTED → PENDING → APPROVED`; только переход к APPROVED создаёт
подтверждённые участия и начисления. Несопоставленное полное ФИО с группой
попадает на ручное разрешение. Нулевой приватный `StudentProfile` создаётся
при импорте контингента, его публикация остаётся отдельным решением.
