EVENT REGISTRATION 1.0 r3 — ОБНОВЛЕНИЕ С r2 · 30 АВГУСТА 2026

Эта инструкция предназначена для обновления уже развёрнутой платформы.
Пакет не содержит MySQL, Docker, systemd units, установочных скриптов,
паролей, TLS-ключей или production-конфигурации.

Состав обновления:
- frontend/web — готовая сборка основного сайта и административной панели;
- frontend/scanner — готовая сборка Scanner PWA;
- backend/*.whl — backend для CPython 3.12, содержащий байткод без исходных .py;
- backend/requirements.txt — зафиксированные runtime-зависимости Python;
- database/migrations — последовательные SQL-миграции MySQL 8.1.0;
- config/backend.env.example — только образец актуальных параметров;
- apache — образец внутренних HTTP VirtualHost за внешним HTTPS proxy;
- MANIFEST.json — SHA-256 файлов поставки.

Обновление r3 предназначено для установленного r2. Новые миграции:
007_email_retry_schedule.sql — расписание повторов отправки писем;
008_event_audience.sql — допустимые категории участников;
009_event_listing.sql — показ мероприятия в публичной афише;
010_event_streams.sql — потоки со своим временем и вместимостью;
011_registration_form_config.sql — конструктор публичной/очной формы и защита повторной отправки.
Миграции 001–006 совпадают с r2 побайтово. Повторно вручную их не выполнять.
MySQL остаётся ровно 8.1.0; данные участников миграции не удаляют.

ЧТО ПОМЕНЯЕТСЯ ДЛЯ ОРГАНИЗАТОРОВ
- В афише вместо календаря — список и фильтры.
- Статусы меняются по московскому времени автоматически: открыта → закрыта → мероприятие идёт → завершено.
  Черновики/архив не публикуются; ручное закрытие сохраняется.
- Можно убрать мероприятие из афиши, сохранив регистрацию по прямой ссылке.
  Это не защита по приглашениям: ссылку можно переслать.
- В новом мероприятии можно заранее создать потоки: участник выбирает один;
  у каждого потока собственные время и лимит. Существующие регистрации без потоков
  автоматически не распределяются: включать потоки нужно до первой регистрации.
- Конструктор отдельно настраивает публичную и очную форму. Имя, фамилия, согласие
  обязательны; остальные поля нового мероприятия необязательны по умолчанию.
  Старые мероприятия сохранят прежние требования до их изменения организатором.
- Если email не указан, билет необходимо сохранить с экрана.
- При ограничении категории (например, только родители) статус участника обязателен.
- Сканер: компактные вкладки, явные ошибки, защита повторного чтения того же QR,
  подтверждение превышения мест с записью в журнале.
- В списке приглашений видны статус письма и повторы. SENT означает принятие SMTP,
  а не гарантированное попадание во входящие: нужно также проверить спам/карантин.
- Письма имеют HTML-шаблон и московское время; отчёты включают потоки.

ВАЖНЫЕ ЗАПРЕТЫ

1. Не заменять рабочий защищённый backend.env файлом backend.env.example.
2. Не размещать backend.env, пароли или секреты в Apache DocumentRoot.
3. Не выполнять database/01_schema.sql для уже существующей рабочей базы.
4. Не смешивать старые и новые файлы frontend/assets.
5. Не удалять каталог MEDIA_ROOT: в нём хранятся загруженные обложки.
6. Не запускать backend как python event_api/main.py.
7. Не менять MySQL 8.1.0 на другую основную версию в рамках этого обновления.

ШАГ 1. ПОДГОТОВКА И РЕЗЕРВНАЯ КОПИЯ

1. Назначить короткое окно обслуживания и запретить новые регистрации на время
   миграции.
2. Остановить email worker, затем API через используемый организацией process
   manager. Apache пока можно оставить запущенным с технической страницей.
3. Создать и проверить резервные копии:
   - базы event_registration;
   - каталога, указанного в MEDIA_ROOT;
   - действующего защищённого backend.env;
   - текущих backend wheel/venv и двух frontend DocumentRoot;
   - действующей конфигурации Apache.
4. До рабочего обновления восстановить копию базы на отдельной MySQL 8.1.0 и
   выполнить обновление там. Чтение дампа не заменяет проверку восстановления.
5. До остановки сервера синхронизировать накопленные offline-отметки всех устройств.
   Не очищать IndexedDB и не переустанавливать PWA при наличии неотправленных отметок.

ШАГ 2. РАСПАКОВКА И ПРОВЕРКА ПОСТАВКИ

1. Распаковать ZIP в новый временный каталог, не поверх рабочей установки.
2. Убедиться, что присутствуют README.txt, MANIFEST.json, backend, frontend,
   database, config и apache.
3. Сверить SHA-256 критичных файлов с MANIFEST.json. Не устанавливать пакет,
   если файл отсутствует или контрольная сумма не совпадает.
4. Убедиться, что сервер использует CPython 3.12 и MySQL 8.1.0.

ШАГ 3. КОНФИГУРАЦИЯ

1. Сравнить действующий защищённый backend.env с
   config/backend.env.example и перенести только отсутствующие параметры.
2. Сохранить прежние реальные значения DATABASE_URL, SESSION_SECRET,
   AUTH_LINK_SECRET, QR_SIGNING_SECRET и SMTP credentials. Не генерировать
   новые секреты при обычном обновлении: это завершит сессии и может нарушить
   проверку ранее выпущенных ссылок/QR.
3. Проверить обязательные значения:
   - NODE_ENV=production;
   - API_HOST=127.0.0.1;
   - публичные CORS_ORIGINS, AUTH_LINK_BASE_URL и PUBLIC_WEB_BASE_URL — HTTPS;
   - MEDIA_ROOT расположен вне DocumentRoot и доступен на запись только
     runtime-пользователю backend;
   - COVER_MAX_BYTES задан согласно политике организации;
   - MIGRATIONS_DIR указывает на каталог migrations из новой поставки.
4. backend.env должен оставаться доступным только runtime-пользователю и
   администратору сервера.

ШАГ 4. МИГРАЦИИ БАЗЫ

1. Использовать отдельную защищённую копию конфигурации для мигратора с
   DATABASE_URL пользователя, имеющего CREATE, ALTER, INDEX и REFERENCES.
   Не передавать пароль в аргументах командной строки или shell history.
2. Создать новый Python venv и установить backend согласно шагу 5, затем
   выполнить до запуска API:

   EVENT_REGISTRATION_ENV_FILE=/etc/event-registration/migration.env \
     /opt/event-registration/releases/NEW/.venv/bin/python \
     -m event_api.migrate

3. Команда применяет только отсутствующие миграции и проверяет checksum уже
   применённых. При несовпадении checksum или SQL-ошибке остановить обновление;
   нельзя вручную помечать миграцию выполненной.
4. Для новой пустой установки вместо этого следовать разделу Database в
   README.txt: 00_create_database.sql, затем 01_schema.sql.

ШАГ 5. УСТАНОВКА НОВОГО BACKEND

Рекомендуется новый каталог релиза, например:

  /opt/event-registration/releases/1.0.0-r3-20260830

В нём выполнить:

  python3.12 -m venv .venv
  .venv/bin/python -m pip install -r backend/requirements.txt
  .venv/bin/python -m pip install --no-deps backend/*.whl

Проверить импорт до переключения рабочего процесса:

  NODE_ENV=test \
  DATABASE_URL=mysql://placeholder:placeholder@127.0.0.1/placeholder \
  CORS_ORIGINS=http://localhost:5173 \
  SESSION_SECRET=sssssssssssssssssssssssssssssssssssssssssss \
  AUTH_LINK_SECRET=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa \
  AUTH_LINK_BASE_URL=http://localhost:5173/auth \
  QR_SIGNING_SECRET=qqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqq \
  PUBLIC_WEB_BASE_URL=http://localhost:5173 \
  CONSENT_URL=http://localhost:5173/privacy \
  CONSENT_VERSION=install-check \
  .venv/bin/python -c "import event_api.main, event_api.bootstrap"

После успешной миграции переключить process manager на новые entry points:

  EVENT_REGISTRATION_ENV_FILE=/etc/event-registration/backend.env \
    /opt/event-registration/releases/NEW/.venv/bin/event-api

  EVENT_REGISTRATION_ENV_FILE=/etc/event-registration/backend.env \
    /opt/event-registration/releases/NEW/.venv/bin/event-email-worker

ШАГ 6. ЗАМЕНА FRONTEND

1. Не копировать новые файлы поверх старого каталога assets.
2. Подготовить два новых каталога рядом с рабочими DocumentRoot:
   - frontend/web для основного домена;
   - frontend/scanner для домена сканера.
3. Проверить владельца и права: Apache требуется только чтение.
4. Атомарно переключить DocumentRoot или управляемый организацией symlink на
   новые каталоги. Старые каталоги пока сохранить для отката.
5. Если конфигурация Apache менялась, адаптировать файл из apache/, выполнить
   apachectl configtest и только после успеха reload Apache.
6. Внешний reverse proxy продолжает принимать HTTPS :443 и передавать запросы
   на внутренний Apache HTTP :80. Прямой доступ пользователей к :80 запрещён.

ШАГ 7. ЗАПУСК И ПРОВЕРКА

1. Запустить API и проверить локально:

   curl http://127.0.0.1:3000/health/live
   curl http://127.0.0.1:3000/health/ready

2. Запустить email worker.
3. Проверить через внешний HTTPS:

   curl https://REAL_WEB_DOMAIN/api/health/live
   curl https://REAL_SCANNER_DOMAIN/api/health/live

4. В браузере проверить:
   - главную страницу без календаря, поиск, фильтры и автоматические статусы;
   - административный вход и роли SUPER_ADMIN/ORGANIZER/SCANNER;
   - создание и изменение мероприятия, обложку и ссылку регистрации;
   - регистрацию участника и обязательное выключенное по умолчанию согласие;
   - категории «Родитель»/«Другое» и запрет неподходящих категорий;
   - выбор одного потока, его лимит и время в билете;
   - независимые обязательные/скрытые поля публичной и очной регистрации;
   - подтверждение превышения мест у назначенного сканировщика;
   - билет/QR;
   - сканирование камерой на реальном HTTPS-устройстве;
   - отправку тестового письма через production SMTP.
5. Для Scanner PWA закрыть все старые вкладки/установленные окна, открыть
   Scanner заново и обновить страницу. Проверить, что загружена новая версия.
   Перед очисткой данных браузера обязательно синхронизировать ожидающие
   offline-отметки посещения.
6. Проверить журнал backend на ошибки, не выводя Cookie, пароли, токены или PII.

ШАГ 8. ПЕРВЫЙ SUPER_ADMIN

На обновляемой системе повторно создавать SUPER_ADMIN не требуется. Только для
первой установки выполнить команду из README.txt. Пароль задаётся владельцем
по одноразовой HTTPS-ссылке; готовый пароль в поставке отсутствует.

ОТКАТ

1. При ошибке до применения миграций вернуть предыдущие backend/frontend и
   запустить прежние процессы.
2. После применения миграций сначала оценить совместимость предыдущего кода.
   Если новые функции уже использовались, откат выполнять только вместе с
   проверенным восстановлением снимка базы и MEDIA_ROOT из одной точки времени.
3. Не запускать r2 поверх данных с новыми потоками: старая версия не учитывает их
   лимиты и настройки форм. Откат после использования r3 требует согласованного
   восстановления: новые записи после точки резервирования будут потеряны.
4. Не удалять новые данные и не выполнять обратный SQL без отдельного плана.
5. Сохранить логи ошибки и MANIFEST.json перед откатом, не включая секреты.
